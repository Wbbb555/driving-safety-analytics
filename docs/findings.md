# 五个不会报错的坑

这篇记的是方法上的问题，不是模型成绩。

共同点是：代码跑得通，AUC 看着也还行，图也画得出来，但结论是错的。五个坑里没有一个会抛异常，所以靠测试和 CI 是抓不到它们的，只能靠事后对着数据一条条核。

下面所有数字都来自 `data/synthetic`，脚本能复算。合成数据里刻意复现了原项目那两个方向反常的指标（吸烟、盲区报警），所以数字可以跟原项目对着看，但量级不能直接比。

| | 坑 | 后果 | 实测偏差 |
|---|---|---|---|
| 1 | 暴露量混杂 | 纯里程特征拿到 0.81 AUC | 残差化后 0.8080 → 0.4995 |
| 2 | 特征选择偏差 | 边选边评，AUC 虚高 | +0.0095 |
| 3 | 系数符号不稳 | 拿单次拟合的符号讲故事 | 8 个指标里 3 个有 28~39% 会翻向 |
| 4 | 分箱泄漏 | WOE 分箱偷看标签 | +0.0075 ~ +0.0115 |
| 5 | 加总身份不成立 | 评分卡没法审计 | 曾差 774.8 和 1106.8 |

## 一、暴露量混杂

只按里程排序，对事故标签的 AUC 就是 0.8074。一个完全不含驾驶行为信息的量，本身预测力就这么强。

不是因为跑得多所以容易出事，是因为里程同时抬高了分子和分母：跑得多的车，事故次数和风险事件次数都多。所有计数型特征都带着这个信号——事件条数、GPS 采样点数、IMU 记录行数。

| 特征 | 原始 AUC | 对数-对数残差化后 |
|---|---|---|
| 轨迹采样点数（纯数据量，零行为信息） | 0.8080 | 0.4995 |
| 事件总条数（暴露量 × 行为率） | 0.8902 | 0.7606 |

采样点数和里程的 Spearman 是 0.9995，它真就是里程的另一种写法。残差化后掉到 0.4995，标准随机水平。事件条数残差化还剩 0.7606，说明里面确实有真信号，只是残差化没法把暴露量和行为率彻底分开。

这里我第一次做错了。当时用原始计数对 log(里程) 回归做残差，采样点数还能到 0.61，看起来像有信号。根因是计数随里程近似幂律增长，对 log 回归之后残差里还留着一条单调曲线。改成对数-对数才掉到 0.50。同一个动作，回归形式选错就会造出看起来像信号的残余，所以脚本里两个口径都打印，把这个对照留着。

最后评分体系全换成率（事件数 / 里程），暴露量在分母里约掉。最强的率指标是车道偏移，AUC 0.8215，也就比纯里程高 0.014。这个数不好看，但它才是真正属于行为的部分。

判据可以这么用：把可疑特征对暴露量做残差化，残差 AUC 掉到 0.5 附近就说明它是纯暴露量。任何「设备上报数据量」类特征都适用，GPS 点数、CAN 报文条数、日志行数都一样。

## 二、特征选择偏差

流程是全样本上按重要性挑 top-k，再用交叉验证评。问题在于挑特征时已经看过全部标签，验证折的标签也参与了选择，CV 就不再独立。

朴素 0.8744，嵌套 0.8649，差 0.0095。这一轮偏差不大，因为用的是树模型重要性，本身不算强选择器。换成单变量 AUC 或 IV 来筛，偏差会大得多，原项目里量到过 +0.051。

比偏差数值更值得看的是 top_k 扫描。k 从 4 扫到 22：

```
0.8682  0.8593  0.8649  0.8720  0.8639  0.8611
```

最高在 k=12。但整条曲线只在 0.0127 里波动，没有单调趋势。66 个正例，这个幅度就是噪声。

所以正确结论是「挑几个特征对泛化没有稳定影响」，「k=12 最好」是过度解读。判别方法是看曲线有没有超出噪声带宽的单调趋势，而不是看最大值落在哪。

处理上只有一条：选择放进交叉验证内层。如果已经做了朴素版，就拿嵌套结果当唯一可信口径，两者之差当偏差估计。

## 三、系数符号不稳

八个指标一起回归，WOE 变换后 VIF 最大 1.53，全部远低于 5。没有严重共线性。

这一点值得强调，因为很多人的第一反应是「系数反号说明共线性严重」。这次的数据不支持这个解释，如果照着这个思路去删变量，方向就错了。

真正更基础的问题是符号本身稳不稳。B=200 次车辆重抽样，统计系数方向符合常识（事件越多越危险）的比例：

```
车道偏移   100.0%        设备异常   72.0%
疲劳       100.0%        分神       68.0%
超速        99.5%        碰撞预警   61.5%
盲区报警    21.0%        吸烟        1.5%
```

分神、碰撞预警、设备异常这三个有 28~39% 的重抽样会翻向。在 500 台车、几十个正例的量级上，某一次拟合出「分神系数是负的」，根本不能当成「分神有害或有益」的证据。

盲区报警是 21%，意思是 79% 的重抽样反号，但没到 95% 的稳定线。既不能说它稳定有害，也不能说它稳定有益。这种两头都不占的指标最危险，因为写作时很容易按需要挑一个方向来讲。

出过一次实际事故：这张表我最初把盲区报警标成「稳定反号」，跟吸烟并列。`check_claims.py` 里那条「不稳和稳定反号两档必须互斥」的断言把它逼出来了。表格每一行单独看都成立，错在分档之间不互斥，读一遍查不出来。

还有个反直觉的地方，是写单元测试时才确认的：WOE 分箱本身会吸收方向。指标值越大出险率越高时，WOE 自动变低，回归系数自然为负。所以标准 WOE 评分卡里「反向指标」并不会产出反号系数。真正的反号只来自抑制效应——两个指标高度相关，弱的那个边际贡献转负。我原以为「把指标设成负向就能复现反号」，实测发现不会，得构造抑制才行。`tests/test_core.py` 里的 `flip_case` 夹具现在显式搜产生反号的种子，搜不到直接 fail，不假装测过。

处理优先级：先做排除法，逐个移除相关指标看符号翻不翻回来；如果确实被强指标吸收，上符号约束（风险因素系数强制不小于 0）或按维度分组建模；排除法也解释不了的，标成「方向待核实」，不许翻译成行为建议。

第三条最容易破。原项目里「吸烟越多出险率越低」这种结果，写成「建议适当吸烟」就是灾难。宁可标待核实、从评分卡拿掉，也不要给它编解释。

## 四、分箱泄漏

WOE 分箱边界是用全部样本的标签算的，然后拿这批边界做交叉验证。验证折的标签已经参与分箱，评估不再独立。

全样本分箱 0.8555，折内分箱 0.8390，偏差 0.0165。`run_task2.py` 里两个无泄漏口径各算一次，分别是 +0.0075 和 +0.0115。偏差不是常数，跟正例比例、分箱数都有关。

凡是拿标签做离散化的都有这个问题：WOE/IV、最优分箱、目标编码、按目标分层的聚类。评分卡项目里尤其容易漏，因为分箱和建模一般写在两个脚本里，跨脚本的泄漏眼睛看不出来。

这里有个专门要避开的错误：不要拿「上一代的全样本分」减「这一代的无泄漏分」当泄漏量，那样会把版本差异算进去。原项目归档文档里就有这个混淆——0.83 对 0.8304，两个数接近到看不出泄漏，但它们来自不同代的模型。正确做法是同一批数据、同一套超参、同一个种子，只切分箱在折内还是折外。

顺带一个更隐蔽的口径问题。把各折验证分拼成一个向量算全局 AUC 时，如果每折分数刻度不同（比如每折各自锚到某个基准分），拼池等于给不同折加了不同常数。本仓库三种口径（种子 0/1/42 平均）：

```
拼池              0.8350
每折中心化        0.8264
逐折算再平均      0.8390
```

差 ±0.007。核过不是泄漏——各折基准分跟折内正例率的 Pearson r 是 -0.085，基本无关。属口径选择，所以两个无泄漏口径我都报。只报一个数的麻烦在于读者会以为那是唯一正确值，换个折算方式就对不上账。

## 五、加总身份不成立

评分卡对外说「总分 = 基准分 + 各项得分」，实际算出来对不上，先后出现过差 774.8 和 1106.8。

三个原因，都不报错：

一，把箱序号当成 WOE 喂进回归。结果八个指标里六个系数变正，全被符号约束截成 0，连车道偏移这种最强指标都被清零。评分卡失去区分度，加总自然也对不上。修法是 `woe[apply_bins(x, edges)]`。

二，加总校验时重复计数。`item_scores()` 返回的 DataFrame 里已经含「安全分」汇总列，校验时对整表 `sum(axis=1)` 等于把汇总列加了两次。修法是先把汇总列排除掉。

三，刻度设计让基准分不可控。常规的 `score = BASE − factor × (Σβ·WOE + β0)` 使基准分完全由 β0 决定，算出来 236.8，业务方看不懂，也没法解释为什么满分不是 1000。

修法是锚定中位车。中位车定 700 分，`基准分 = 700 − median(raw)`，于是

```
安全分 = 基准分 + Σ 各项得分
```

恒成立，内存口径实测最大差 0.000000。这个恒等式是评分卡能被审计的前提：司机问「我为什么扣这一分」的时候，答案得能逐项加回总分。

有个细节容易搞错：锚定的是 median(总分) = 700，不是 median(各项得分之和) = 0。`base_offset` 的作用是把中位车的原始贡献整体平移到 700，所以原始贡献的中位数一般不是 0。这条也在单元测试里钉住了。

判据要硬：差必须是 0，不是差不多。但「差多少」要分清口径——**内存里算是 0.000000，把导出的 `task2_item_scores.csv` 的列直接相加则是 0.3**，因为八项各舍到 0.1，累计上界 0.4。而差 774.8 是结构错误（箱序号当 WOE）。三种情况都得查，但不能混着说，混着说就等于没查。

## 附：一个方向性 bug

初版 `leaky_auc` 用 `decision_function` 之后又取了负，算出泄漏 AUC 0.1535、乐观偏差 -0.6815。数字荒谬到一眼能发现，但如果偏差在 +0.02 这个量级，就发现不了了。

根因是方向混用。安全分越高越安全，风险概率越高越危险，反的。混用会把 AUC 悄悄变成 1−AUC，不报错、不崩溃，只是结论全反。

现在两个函数都在 docstring 里写清了方向约定：`oof_auc` 用安全分（取负使 AUC 大于 0.5），`leaky_auc` 用风险概率（不取负）。`test_score_direction_high_is_safe` 钉住这个不变量。

## 这些数字能怎么用

能拿来当偏差量级的参照，前提是样本量和正例率接近。也能当「这个坑值多少分」的量化依据去说服别人做嵌套验证。五个坑的判据可以当代码审查清单用。

不能当通用常数。偏差大小取决于正例比例、分箱数、特征相关性，换了数据就不是这些数。也不能当模型效果，这里所有 AUC 都是合成数据上的，跟任何真实车队无关。更不能当因果结论，评分卡是排序工具，「车道偏移扣分最多」不等于「少压线就能少出事故」。
