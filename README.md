# 驾驶安全风险预测与可解释评分卡

两件事：给每台车一个事故风险排序，再把排序拆成一张能逐项看懂的安全评分卡。

模型本身没什么特别。这个仓库主要想记的是做这件事的过程中踩到的五个坑。它们都不会让代码报错，跑出来的 AUC 也都不难看，但结论是错的。

展开写在 [docs/findings.md](docs/findings.md)，这里只是索引。

## 数据

仓库里的数据全部由脚本生成，车号是假的，跟任何真实车队无关。

原始数据是企业车辆的轨迹和司机行为记录，受保密条款约束，不能公开。合成数据只保留结构：500 台车、61 天、8 个评分指标，分表形态跟真实的一致，这样方法能端到端跑起来。

生成器里我故意把吸烟和盲区报警设成负向，因为真实项目里这两个指标的方向就是反的，想原样复现出来。

![十分位出险率](docs/figures/task2_decile.png)

## 跑起来

```
pip install -r requirements.txt
python scripts/generate_synthetic.py
python scripts/demo_traps.py

python src/task2/run_task2.py

```

全部跑完 91 秒（Windows 11 / Python 3.12，单核）。不用改路径，数据目录按 `--data` > `DSA_DATA_DIR` > `data/synthetic` 取。`generate_synthetic.py` 是生成器，用 `--out`。装了 make 的话 `make all` 跑前六步。

下文所有数字都能用 `demo_traps.py` 当场跑出来核。但要注意它们是 500 台车、66 个正例这个样本量下的值，不是通用常数。

## 坑一：数据量本身就是个很强的特征

只按里程排序，对事故标签的 AUC 就有 0.8074。不用建模。

所以任何跟里程相关的计数型特征都自带这个信号。轨迹采样点数是纯数据量，不含一点行为信息，原始 AUC 0.8080，跟里程的 Spearman 0.9995，它就是里程换了个写法。对数-对数残差化之后 0.4995，随机水平。事件总条数原始 0.8902，残差化后还剩 0.7606，说明里面确实有真东西，但残差分不干净。

中间我走过一次弯路。最开始拿原始计数对 log(里程) 回归做残差，采样点数还能到 0.61，看着像有信号。实际是计数随里程近似幂律增长，对 log 回归之后残差里仍留着一条单调曲线。改成对数-对数才掉到 0.50。脚本里两个口径都打印，就是为了留着这个对照。

最后评分体系全部换成率（事件数除以里程），暴露量在分母里约掉。最强的率指标是车道偏移，AUC 0.8215，只比纯里程高 0.014。这 0.014 才是真正属于行为的。

## 坑二：挑完特征再交叉验证，AUC 会虚高

全样本上按重要性挑 top-k，然后拿同一批数据做交叉验证。挑的时候已经看过全部标签，验证折的标签也参与了选择，CV 就不独立了。

朴素口径 0.8744，嵌套口径 0.8649，差 0.0095。这里用的是树模型重要性，本来就不是强选择器，所以差得不多。换成单变量 AUC 或者 IV 来筛会明显得多，原项目里量到过 +0.05 量级。

更值得说的是 top_k 扫描。从 4 扫到 22，AUC 分别是

```
k=4  0.8682    k=12 0.8720
k=6  0.8593    k=16 0.8639
k=8  0.8649    k=22 0.8611
```

最高在 12。但整条曲线只在 0.0127 的范围内晃，没有单调趋势。66 个正例的样本量，这个幅度的跳动就是噪声。

所以我写的是「挑几个特征对泛化没有稳定影响」，不是「12 个最好」。拿这种扫描的排名当结论，是这类比赛里最常见的过度解读。

## 坑三：系数反号，先怀疑符号本身稳不稳

八个指标一起回归，WOE 变换后 VIF 最大 1.53，全部远低于 5。没有严重共线性。很多人一看到反号就说共线性，这次的数据不支持这个解释。

真正的问题更基础一些。B=200 次车辆重抽样，统计系数方向符合常识（事件越多越危险）的比例：

```
车道偏移   100.0%      设备异常    72.0%
疲劳       100.0%      分神        68.0%
超速        99.5%      碰撞预警    61.5%
盲区报警    21.0%      吸烟         1.5%
```

分神、碰撞预警、设备异常这三个，有 28~39% 的重抽样会翻向。也就是说某一次拟合出「分神系数为负」，根本不能当证据，换个种子就没了。

盲区报警那一栏是 21%，意思是 79% 的重抽样反号，但没到 95% 的稳定线。既不能说它稳定有害，也不能说它稳定有益。这种两头都不占的指标最麻烦，写作时很容易按需要挑一个方向讲。

处理上我是这么排的：先做排除法，逐个移除相关指标看符号会不会翻回来；如果确实是被强指标吸收，就上符号约束（风险因素系数强制不小于 0）；如果排除法也解释不了，就标成「方向待核实」，不翻译成行为建议。

第三条最容易违反。真实项目里「吸烟事件越多、出险率越低」这种结果，一旦写成「建议适当吸烟」就是事故。宁可标成待核实、从评分卡里拿掉，也不要给它编一个解释。

## 坑四：WOE 分箱偷看了标签

分箱边界是用全部样本的标签算的，然后拿这批边界做交叉验证。验证折的标签已经参与分箱了。

全样本分箱 0.8555，折内分箱 0.8390，乐观偏差 0.0165。`run_task2.py` 里两个无泄漏口径各算一次，量到的是 +0.0075 和 +0.0115。偏差大小不是常数，取决于正例比例和分箱数。

凡是拿标签做离散化的都有这个问题：WOE/IV、最优分箱、目标编码。评分卡项目里尤其容易犯，因为分箱和建模通常写在两个脚本里，跨脚本的泄漏用眼睛很难看出来。

这里有个坑要特意避开：不要拿「前一代的全样本分」减「这一代的无泄漏分」当泄漏量，那样会把版本差异算进去。原项目归档里就有这种混淆，0.83 对 0.8304，数字接近到看不出泄漏，但两者来自不同代的模型。正确做法是同一批数据、同一套超参、同一个种子，只切分箱在折内还是折外。

另外，把各折验证分拼成一个向量算全局 AUC 的时候，如果每折分数刻度不同，拼池等于给不同折加了不同常数。本仓库三种口径都算过：

```
拼池            0.8350
每折中心化      0.8264
逐折算再平均    0.8390
```

差 ±0.007。核过不是标签泄漏（各折基准分与折内正例率的 r 是 -0.085），是口径选择问题。所以两个无泄漏口径我都报，只报一个数容易让人以为是唯一正确值。

## 坑五：加总对不上，评分卡就没法审计

评分卡说「总分 = 基准分 + 各项得分」，实际算出来对不上，出现过差 774.8 和 1106.8 两次。

三个原因，都不报错。一是把箱序号当成 WOE 喂进回归，结果八个指标里六个系数变正，全被符号约束截成 0，连车道偏移都被清零，评分卡直接失去区分度。二是加总校验的时候对整表求和，而表里已经有「安全分」汇总列，等于把汇总加了两次。三是刻度设计让基准分完全由 β0 决定，算出来 236.8，业务方看不懂。

修法是锚定中位车：中位车定 700 分，`基准分 = 700 − median(raw)`。这样总分 = 基准分 + 各项得分 恒成立，内存里算出来的最大差是 0.000000。评分卡能不能被审计就取决于这个恒等式成不成立——司机问「我为什么扣这一分」的时候，答案得能一项项加回总分。

这里有个容易说错的地方：如果你直接下载 `outputs/task2_item_scores.csv`，把八个「_得分」列和「基准分」加起来，跟「安全分」能差到 **0.3**。这不是恒等式破了，是导出时每项被舍到 0.1，八项累计的上界是 0.4。两个数都对，但口径不同，写的时候必须分开讲——**差 0.3 是舍入，差 774.8 是结构错误**，混在一起说就等于没查。

判据要硬：差必须是 0，不是差不多。差 0.2 是舍入残留，差 774.8 是结构错误,两种都要查,但不能混着说。

## 任务一

`src/task1/run_task1.py`，17 维特征：8 个指标的每千公里率、速度均值、夜间行驶占比、IMU 四类事件率、IMU 覆盖率。

验证用 StratifiedGroupKFold 按车分组。同一台车不能同时出现在训练折和验证折，否则模型记的是车不是规律。三个模型做秩融合，不做概率平均，因为不同模型的校准程度不一样，直接平均等于假设它们可比。

```
LR-L1        0.8618
ExtraTrees   0.8531
RandomForest 0.8367
秩融合        0.8557
```

融合没超过最好的单模型。样本量小、模型之间相关性高的时候这很正常，融合降方差但不会凭空造信息。很多报告只写融合结果不写单模型，读者容易以为融合一定更好。

输出列里 `risk_score` 是融合后的秩均值，`risk_prob` 是把它线性映射到 0~1 的相对位置，不是校准过的出险概率。要真概率得另做 Platt 或 isotonic，这里没做。之前把秩分挂在 `risk_prob` 这个名字下，是个实打实的误导。

## 任务二

`src/task2/run_task2.py`，标准 WOE 评分卡，8 个指标、每个 2~5 箱、单调约束、符号约束、逐项得分明细。

```
OOF AUC 折内分箱 逐折平均   0.8390 ± 0.0027
OOF AUC 折内分箱 拼池       0.8350 ± 0.0042
OOF AUC 全样本分箱（泄漏）   0.8465
逐项加总与总分最大差         0.000000（内存口径）
                             0.3（直接加导出 CSV，舍入残留）
分档出险率 高/中/低          32.3% / 6.0% / 1.2%
十分位 Spearman             -0.9510
```

拼池口径为什么会有噪声：每折的基准分是按该折训练集中位原始分锚定到 700 的，五折分别是 183.5 / 134.1 / 122.8 / 96.9 / 128.3，拼在一起等于给不同折平移了不同常数。

还有个方向性 bug 值得记一下。初版 `leaky_auc` 用 `decision_function` 之后又取了负，算出泄漏 AUC 0.1535、乐观偏差 -0.6815，数字荒谬到一眼能发现。但要是偏差在 +0.02 这个量级就发现不了。根因是方向混用：安全分越高越安全，风险概率越高越危险，反的。混用会把 AUC 悄悄变成 1−AUC，不报错不崩溃，结论全反。现在两个函数都在 docstring 里写清了方向。

## 已知问题

这些是做完之后自己列的、也没完全解决的问题，留着是因为它们决定了上面那些数字能怎么用。

1. 没有独立测试集。所有 AUC 都是 OOF 自评。
2. 标签是同期不是未来。赛题要的是「未来事故风险」，但能拿到的标签和特征在时间上重叠，严格说是同期关联。
3. 大量特征是里程代理。坑一量化了，但残差化只处理了线性部分。
4. IMU 覆盖率只有 48.7%，近一半车没有可用传感器数据，而有没有数据本身跟车型用途相关，是选择偏差。
5. 样本量不够。500 台车、66 个正例，符号稳定性那张表就是直接证据。
6. 原始特征集有 300 多对 |r| > 0.9，冗余得很厉害。
7. 十分位不是严格单调，第 5、6 档是 4% 到 6%。

另外这个仓库不做的事：不复现真实数据（数据不能公开，仓库里一行都没有），不声称能上生产（样本量摆在那），不给因果结论（评分卡是排序工具，「车道偏移扣分最多」不等于「少压线就能少出事故」），不引用任何外部行业基准。

## 一些零碎的

测试只钉性质不钉数字。17 项里没有一条断言具体 AUC——AUC 会随种子和 sklearn 版本漂，钉死了过几天就红，然后被加 skip，就没用了。钉的是：分箱边界严格递增、每个样本恰好落一个箱、符号约束后 β 都不大于 0、逐项加总恒等于总分、中位车恒在 700 分、脱敏跨文件一致。其中 `flip_case` 夹具是显式搜能产生反号系数的种子，搜不到就 fail，不装通过。

`check_claims.py` 管的是另一件事：文档里的数字会不会过期。它把 README 和 findings 里的结论写成 22 条断言，CI 里跑。这个脚本抓出过一个真错误——我最初把盲区报警写成「稳定反号」，跟吸烟并列，但它只有 79% 反号，没到 95%。表格每一行单独看都对，错在分档之间不互斥，光读一遍查不出来。

CI 放在 `docs/ci/ci.yml` 而不是 `.github/workflows/`，因为推送的时候 token 没有 workflow scope，GitHub 直接拒了：

```
refusing to allow a Personal Access Token to create or update workflow
`.github/workflows/ci.yml` without `workflow` scope
```

不想为一个配置文件去要更高权限，就先放这儿。要用的话在浏览器里新建 `.github/workflows/ci.yml` 把内容粘过去，或者补了 scope 之后 `cp` 过去。CI 会先清空 `data/synthetic` 和 `outputs` 再从零跑，否则它可能一直在用仓库里已提交的产物，查不出生成器已经跑不出这份数据这类退化。

`anonymize.py` 是脱敏工具，把真实车号换成 `VEH_cd81d4c3` 这种代号。代号直接由 `sha256(SALT + 车号)` 派生，所以同一个车号在任何文件里都是同一个代号，跟文件里有几台车无关。

这个工具被实测打回过两次。第一版用 `hash % 500` 往 500 个坑里塞，按生日问题必然撞号。第二版改成按哈希排序后依次分配 `VEH_0001`，单文件里唯一了，但代号取决于这份文件里有多少台车——500 台和 400 台子集跑出来有 397 个不一致，评分结果 50 台和明细 500 台对不上账。现在这版跟文件内容无关，撞了会直接报错，不静默合并。
